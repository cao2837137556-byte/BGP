# 文献吸收_系统提升规划_v01

更新时间：2026-04-11

用途：把当前已读 BGP 安全论文中对本项目有用的实验口径、特征工程、验证方法和后续能力规划沉淀下来。本文不是论文正文，后续可作为实验设计与写作背景材料。

## 1. 当前判断

我们当前系统的强项已经不只是“链路跑通”，而是形成了比较完整的分层证据闭环：candidate 做前置压缩，gate 控制 high 纯度，augment 对 uncertain 子集做小规模补证，E7 已证明 collector 可见度变化会导致保守退化。

到 2026-04-11 为止，已知真实事件验证也已推进到比 E8-C 更扎实的状态：E9-A 扩展观测点后，`3/3` 公开事件都获得了系统响应，口径为 `2 high + 1 needs_review`。这说明当前短板已经从“完全看不到”转移到“某些 route-leak 风格事件为何停在 review 而不是 high”。

和 BEAM、DFOH 这类顶会系统相比，当前最大差距仍然不在“是否存在有效信号”，而在 benchmark 规模、跨 collector 稳定性、外部证据验证层和 forged-origin / route-leak 专项特征上。下一阶段不应急着引入端到端新模型，优先级更高的是：固定 E9-A 结论、做 E9-B 专项特征审计、扩真实事件 benchmark，并把 partial observability 作为论文主线而不是缺陷掩盖。

## 2. 逐篇可吸收点

### DFOH / NSDI 2024：A System to Detect Forged-Origin BGP Hijacks

核心启发：

- 这是和我们最接近的 forged-origin 对标系统。
- 它把 forged-origin detection 归约为判断 AS-PATH 中的新 AS link 是真实连接还是伪造连接。
- 它不是简单遇到 unseen link 就报警，而是用多类特征和训练策略抑制正常新链路造成的误报。
- 关键结果：检测 `90.9%` forged-origin hijacks，约 `5min` 内完成；全网每天约 `17.5` 个 suspicious cases。

可迁移到我们系统：

- 在 candidate / scoring 层加入 forged-origin 专项特征组，不改变主链结构。
- 重点特征方向：new AS link、拓扑变化、peering 相似性、AS-path pattern、bidirectionality。
- 训练策略不能直接随机采负样本，需要考虑 AS 拓扑层级偏置，否则 stub-to-stub 负样本会过多，模型会看起来好但真实 forged-origin 场景弱。
- DFOH 的输出可作为我们后续 E9 的强 baseline 或对照组。

建议动作：

- 启动 `E9-A known-event benchmark`：优先复用 DFOH/BEAM 类论文中的公开事件口径，目标从 E8-C 的 `3` 个扩到 `10~18` 个。
- 启动 `E9-B forged-origin feature audit`：在现有 scored candidates 上补统计 new_link / unseen_link / path-pattern / bidirectional evidence 是否可得。

### Metis / ISCC 2023：Detecting Fake AS-PATHs based on Link Prediction

核心启发：

- Metis 同样关注 fake AS-PATH，但更偏 link prediction，用 GNN 判断 unseen link 是否可信。
- 它指出 naive unseen-link alarm 会带来大量 false positives。
- 结果方向：GNN link predictor 可达到较高 AUC；fake AS-PATH detection precision/recall 超过 `80%`；部署中可节省约 `80%` 验证开销。

可迁移到我们系统：

- 不建议现在直接上 GNN。
- 可先吸收它的分层逻辑：unseen link 不是直接 high，而是作为弱证据进入 candidate/scoring，再由 gate 控纯度。
- 可把 unseen link 切分为 Type-1 / Type-2 之类更细的结构证据，避免把所有 unseen path 混成一个规则。

建议动作：

- 在 E9-B 中把 `unseen_path_for_prefix_origin` 拆成更细的路径证据字段。
- 建一个 `normal_unseen_link` 对照池，避免我们后续 forged-origin 特征只学到“新链路=坏”。

### HEAP / JSAC 2016：Reliable Assessment of BGP Hijacking Attacks

核心启发：

- HEAP 不是新的检测器，而是告警验证器，目标是减少 false positives。
- 它用三类证据过滤/解释告警：IRR 管理关系、拓扑推理、SSL/TLS 证书稳定性。
- 评估中看到 `14,050` 个 subMOAS events，HEAP 可覆盖 `11,222` 个，并能 legitimized `10,666` 个；对 BGPmon real alarms 的交叉检查中仍发现约 `8.24%` false positives。

可迁移到我们系统：

- E8-B 的 evidence grading 方向是对的，但还不够系统。
- 我们可以把外部验证从“临时挂载”升级为稳定的 `validation layer`。
- 目前可优先做 IRR/WHOIS/RPKI/CAIDA/communities；SSL/TLS 或主动扫描属于后续选做，不能现在变成硬依赖。

建议动作：

- 启动 `E9-C evidence validation layer`：把 E8-B 的 topology/communities 结果扩展为标准字段。
- 新增证据等级：system-only suspicious、control-plane supported、externally corroborated、needs manual review。

### BEAM / USENIX Security 2024：Learning with Semantics

核心启发：

- BEAM 的强点是大规模真实事件 benchmark 和实际部署背书。
- 它用 `18` 个 RouteViews datasets、超过 `11B` 条 route announcements，检测 `18/18` confirmed anomalies。
- 它还做了 ISP 一个月部署，处理约 `152M` live announcements，发现 `497` true anomalies，平均 false alarms `1.65/day`。

可迁移到我们系统：

- 我们不能用 E8-C 的 `1/3` 去和 BEAM 的 `18/18` 平行比较。
- 我们需要把 E8-C 升级成 known-event benchmark，而不是继续把它当作案例补充。
- BEAM 的告警命中口径值得借鉴：target prefix 命中，且 responsible/misbehaved AS 也匹配。

建议动作：

- 启动 `E9-A known-event benchmark`，最终输出 hit / partial-hit / miss-with-reason。
- 每个事件必须包含 `prefix_match`、`origin_match`、`attacker_as_match`、`responsible_as_match`、`match_strength`。

### NDSS 2026 SHAMAN：Understanding the Stealthy BGP Hijacking Risk in the ROV Era

核心启发：

- partial ROV deployment 会产生 stealthy hijacking：恶意路线不一定到达 victim 的控制面，但流量仍可能经 legacy AS 被导向 hijacker。
- 它通过 RouteViews routing table discrepancies 抓取潜在事件：两个月内 `1,393` potential incidents，最终经 RPKI/IRR/WHOIS 验证出 `318` high-confidence incidents，覆盖 `2,178` routes。
- 它强调 stealthy hijacking visibility 对 vantage point selection 很敏感。
- SHAMAN 使用 victim-target-hijacker 三元组模型做风险评估；报告总体成功概率 `14.1%`，特定目标场景可达 `99.5%`，对真实数据验证最高 `95.9%` incident-level accuracy。

可迁移到我们系统：

- 这篇非常支持我们的 partial observability 主线。
- 它提醒我们：低可见度不是简单缺陷，而是攻击面本身的一部分。
- 但我们当前系统还没有 ROV/ROA 状态和 victim-target-hijacker 三元组口径。

建议动作：

- 将 E8-A 的 D 类 stealth 候补池升级为后续 `E10 stealthy/low-visibility study`。
- 增加 RPKI/ROV 相关字段作为外部证据挂载，不要立即进入核心检测链。

### USENIX Security 2023 Hlavacek：Insights into RPKI Validation

核心启发：

- 该文关注 ROV deployment 与 invalid-route propagation。
- 关键结论：超过 `27%` AS enforce RPKI filtering；IXP route servers 的 ROV 主要是局部保护，对全球传播限制有限；Tier-1 provider 的 ROV 更能限制 hijack spread。
- 它强调 ROV 测量中的 false positive / false negative 问题，需要 path-aware 方法，而不是单纯增加 injection points。

可迁移到我们系统：

- 对我们最有用的是 ROV/invalid route 的外部背景和可见度解释。
- 在解释 E7 collector 差异时，可以引用“观测点、IXP、Tier-1、ROV 部署位置会显著影响可见性与传播”的思路。

建议动作：

- 在后续 E9/E10 结果表中加入 `rpki_state`、`rov_context_available`、`possible_rov_visibility_bias` 这类字段。

### 2024 NO_EXPORT stealth attack：Global BGP Attacks that Evade Route Monitoring

核心启发：

- 它指出 BGP monitoring 依赖“看见恶意公告”，而 NO_EXPORT sub-prefix hijack 可以让攻击影响大但对监测系统不可见。
- 实验中该攻击对 RouteViews、RIPE RIS、Cisco Crosswork Cloud、ThousandEyes 都不可见；作者还在四个 Tier-1 网络中验证 NO_EXPORT 行为。
- 仿真显示，即便只利用确认易受影响的网络，攻击仍可影响约 `23%` Internet 到随机目的地。

可迁移到我们系统：

- 这篇直接支持我们的“partial observability 不是实验缺陷，而是威胁模型组成部分”。
- E8-B 已解析 communities，这是正确方向，但需要把 NO_EXPORT / NO_ADVERTISE 从辅助字段升级为正式解释字段。

建议动作：

- 在 E9-C 中固定 communities 解析，明确输出 `has_no_export`、`has_no_advertise`、`communities_unavailable`。
- 对低可见度 high_priority 样本增加 `stealth_hint` 字段：低 collector_count + suspicious communities + strong structural evidence。

### Estimating the Impact of BGP Prefix Hijacking

核心启发：

- 这篇不是检测，而是 hijack impact estimation。
- 它把 hijack impact 定义为被感染 AS 的比例，并讨论 public monitors 的非均匀/相关性会导致估计误差。
- 关键观点：只用 RouteViews/RIPE 这类 public monitor 会受 monitor location correlation 影响；数据面 ping/RIPE Atlas 可以补充控制面。

可迁移到我们系统：

- 这可以作为后续“impact/severity scoring”的依据，而不是当前 detection 主链的核心。
- 我们当前 risk_score 更像 suspiciousness，不是 impact。后续论文里必须区分 detection priority 和 impact severity。

建议动作：

- 暂缓影响范围估计，不进入 E9 第一优先级。
- 后续如果要做 severity，可新建 `impact_score`，不要混入当前 `risk_score`。

### ISP Weakly Supervised Learning / ICNP 2021

核心启发：

- 该文通过 teacher systems 生成弱标签，再用 self-attention LSTM 做去噪与泛化。
- 它强调 BGP anomaly 缺少可靠标签，弱监督可作为折中。
- 特征方向包括 prefix features、peer features、AS-volume features、AS-PATH features。

可迁移到我们系统：

- 目前不建议直接上 LSTM，因为会稀释我们分层可解释主线。
- 但它的 teacher-student 思路可用于后续：用 BGPStream/DFOH/BEAM-like known events/我们自己的高置信 E8-B 事件形成弱标签池。

建议动作：

- 作为 E11 以后备选，不进入下一轮主线。
- 如果后续启用学习化增强，优先插入评分层，不替代 candidate/gate/augment。

## 3. 下一阶段建议路线

### E9-A：known-event benchmark 收口与扩容

目的：先把当前 `3/3 response = 2 high + 1 needs_review` 的结果正式收口，再扩到更像 benchmark 的规模。

最小目标：

- 固定当前 `3` 个事件的正式响应表格和结论。
- 事件数从 `3` 扩到 `10~18`。
- 优先选择 DFOH/BEAM/公开安全报告中具有明确 time window、prefix、attacker/responsible AS 的事件。
- 输出 `high_hit`、`needs_hit`、`low_hit`、`miss_with_reason`。
- 未命中必须细分：`no_visibility`、`no_event_constructed`、`weak_signal_not_enough`、`fell_into_low`、`type_mismatch`。

建议标签：

- `known_events_benchmark=可支撑真实能力背书`
- `known_events_benchmark=部分支撑`
- `known_events_benchmark=需扩容复查`

### E9-B：forged-origin / route-leak 专项特征审计

目的：对齐 DFOH/Metis，把 forged-origin 的核心证据补到现有链路中，同时专门处理 Google-Verizon 这类 route-leak 风格事件为什么停在 `needs_review`。

优先特征：

- new_as_link_count
- unseen_link_position
- path_link_seen_before
- bidirectional_link_hint
- path_pattern_degree_delta
- peeringdb_overlap_hint（若数据可得）
- suspicious_link_near_origin

原则：

- 先做审计和离线统计，不立刻改 final label。
- 仍保持主链结构：candidate -> scoring -> gate -> augment -> final。

当前进展：

- 已完成 Google-Verizon 单事件专项审计。
- 当前已确认：该事件在扩展可见度后不再卡在 `no_visibility` 或 `candidate miss`，而是稳定进入 `needs_review`。
- 已做出一条窄范围 route-leak review 保留规则，用于把这类事件从 miss/low 推进到 `review`，但该规则目前仍应视作专项实验结果，不建议直接并入默认生产主链。

### E9-C：外部证据挂载升级

目的：把 E8-B 的外部验证从一次性脚本升级成稳定验证层。

优先字段：

- rpki_roa_state
- irr_org_match
- as_org_match
- topology_violation
- communities_no_export
- communities_no_advertise
- relationship_unknown_rate
- validation_grade

原则：

- 外部证据先用于 validation / grading，不直接作为强制 high 条件。
- 不引入不可自动获取的数据源作为硬依赖。

### E10：stealth / low-visibility 专项研究

目的：把 partial observability 从局限转成贡献点。

优先问题：

- 低 collector_count 但 high_priority 的样本是否具有结构性证据？
- communities / NO_EXPORT 是否能解释部分不可见性？
- route-views.sg 与 rrc00 视角差异是否能推广到更多 collectors？
- visibility drop 是保守降级还是直接漏检？

## 4. 系统升级库存盘点

本节记录后续可插入系统的“武器库”。它不改变当前优先级：下一步仍先做 `E9-A known-event benchmark`，再根据未命中原因决定是否启用这些插件。

### 4.1 核心杀手锏：隐蔽威胁与低可见度

可储备能力：

- BGP Communities 解析：重点字段为 `NO_EXPORT`、`NO_ADVERTISE`、`NO_EXPORT_SUBCONFED`。
- 低可见度反向利用：低 `collector_count` / `visibility_count` 不能一律视作噪音，若同时具备结构异常、子前缀、更具体路由、可疑 communities，应提升 review 或 high 关注度。

工程落点：

- `build_event_units.py`：提取并规范化 communities 字段。
- Candidate 层：增加 `suspicious_community_hint`、`low_visibility_structural_combo` 这类弱规则。
- Augment 层：把低可见度 + 结构异常 + communities 作为补证组合。

保守边界：

- `NO_EXPORT` 不是单独的攻击铁证，合法 TE 或运营策略也可能使用 communities。
- “低可见度”只能作为上下文增强，不能绕过 gate 直接保送 high。

### 4.2 高级语义特征：拓扑、商业关系与路由角色

可储备能力：

- AS Hegemony：衡量某 AS 对某前缀/路径的历史核心地位。
- Routing Role Semantics：借鉴 BEAM，用 AS 角色剧变解释异常，而不是直接引入黑盒 embedding。
- Bidirectionality & Peering：用多 VP、IRR、PeeringDB 或可见双向路径降低正常新链路误报。

工程落点：

- Score 层：加入 `hegemony_delta`、`role_change_hint`、`path_role_shift_score`。
- Gate 层：对高可信 peering/bidirectional evidence 降级误报风险。
- 分析脚本：先离线审计字段可得性，再决定是否接入主链。

保守边界：

- AS Hegemony 和 PeeringDB 都需要额外数据质量控制，不应在 E9-A 前强行接入。
- Routing role 如果用学习模型实现，容易偏离当前白盒分层主线，应暂放 E11 或之后。

### 4.3 外部实锤证据源：验证闭环

可储备能力：

- CAIDA AS relationship：继续用于 rel_seq、valley-free 判断、relationship_unknown_rate。
- RPKI/ROA：补 `rpki_state`、`origin_validity`、`maxLength`、`invalid_reason`。
- IRR/WHOIS/AS-org：补组织归属、合法授权、同组织 MOAS 解释。

工程落点：

- E9-C evidence validation layer：统一输出外部证据字段和 `validation_grade`。
- E8/E9 case cards：把外部证据挂到案例模板里，用于论文 case study。

保守边界：

- RPKI invalid 是强外部支持，但历史 ROA 快照和当时状态必须对齐，不能用当前 ROA 直接倒推历史攻击。
- Valley-free 违规若 unknown 边太多，应输出 `uncertain`，不应过判为 `yes`。

### 4.4 主动搁置方案：学习化评分与二阶段模型

当前结论：

- 学习化评分层可作为 E11+ 储备，不进入下一轮主线。
- uncertain 子集二阶段模型暂不启动，除非 E9-A/E9-B 显示大量真实事件稳定卡在 needs_review 且白盒补证无法解释。

当前登记方式：

- 保留一个正式后续环节：`E11-A 学习化评分层（预留）`。
- 接入边界固定为：只进入评分层，不替代 candidate / gate / augment / final 的白盒链路。
- 目标形式优先考虑 `residual scorer / reranker / calibration layer`，而不是端到端黑盒替换。
- 当前只做“阶段登记”，不进入本轮实现；待 E9/E10 主线收口后，再结合更具体模型方案单独设计。

搁置原因：

- 当前分层白盒链条是论文核心卖点，过早引入深度学习会稀释可解释性。
- 真实事件 benchmark 和外部验证还没补强，先上模型会让归因变复杂。

## 5. 对论文定位的直接影响

当前不建议把论文定位成“比 BEAM/DFOH 全面更强的检测器”。更稳的定位是：

- 面向 weak-signal forged-origin 场景的分层检测与验证框架。
- 重点解决证据不完整、可观测性不足时的保守分流与可解释告警。
- 通过 gate/augment/visibility ablation 证明分层分工。
- 通过 known-event benchmark 和 external validation 证明真实事件响应能力。

当前必须补强：

- 公开真实事件 benchmark 规模。
- forged-origin 专项特征。
- RPKI/IRR/communities 等外部证据挂载。
- 多 collector / 多时间窗可见度分析。

## 6. 本轮阅读结论

这批文献说明：A 区级别的 BGP 安全系统论文不能只靠一个主链跑通和几个案例解释。需要同时具备大规模真实事件 benchmark、强对照、低误报验证、外部证据挂载和可见度边界解释。

对我们而言，最值得立刻吸收的是 DFOH 的 forged-origin feature pipeline、BEAM 的 known-event benchmark 强度、HEAP 的 evidence validation 思路、SHAMAN/NO_EXPORT 论文对 partial observability 的威胁模型支撑。

下一步优先级：`E9-A 正式收口` > `E9-B forged-origin / route-leak feature audit` > `E9-C known-event benchmark 扩容` > `E10 stealth/visibility study` > `E11-A 学习化评分层（预留）`。暂不建议直接进入深度学习或端到端模型替换。
